# The flavor set is layered, not one list

There is no single "list of flavors" in this repo. `flavorNames` in `src/flavor.ts`
(`["easy-cheese", "hallouminate", "sliced-bread", "cheeselord"]`) is the **canonical**
set; every other surface admits a deliberate *subset* of it, and the subset differs by
surface for a reason. Adding or removing a flavor means editing several of these on
purpose — they are not meant to be kept identical.

| Surface | Admits | Why this subset |
|---|---|---|
| `flavorNames` (`src/flavor.ts`) | all 4 | The canonical union. `FlavorName` derives from it. |
| Starlight themes (`src/starlight.ts`) | 3 — `Extract<FlavorName, "easy-cheese" \| "hallouminate" \| "sliced-bread">` | `cheeselord` is excluded: it is the portal identity (dark-only, generated by `generatePortal`), not a docs theme a Starlight site would install. |
| Social-card classes (`cardClass` in `src/social-card.ts`) | all 4 | Every flavor gets exactly one composition CSS class: `fresh-wheel` / `signal-through-the-melt` / `since-sliced-bread` / `norse-cheese-lord` (defined in `styles/social-card.css`). |
| Preview builds (`previewFlavors` in `preview/scripts/flavor.mjs`) | 2 — `easy-cheese`, `hallouminate` | Only these two ship an Astro docs site the preview builds per-flavor; the `cheeselord` portal page is emitted directly by `portal.mjs`, not built as a flavor site. See [[preview-app-split]]. |

## `composition` is a separate taxonomy from the card CSS classes

`FlavorDefinition.socialCard.composition` (`src/index.ts`) is a 3-value **abstract**
descriptor — `"workshop" | "signal" | "monument"` — used when validating a flavor
definition. It is *not* the same thing as the four `cardClass` CSS class names in
`social-card.ts`, and the two are not 1:1 (3 vs 4). Do not conflate the composition
taxonomy with the rendered card class; `contracts.test.mjs` pairs, e.g., an
easy-cheese ("fresh-wheel") flavor with `composition: "workshop"`.

## Gotcha: `schemas/flavor.schema.json` is published but unenforced

The JSON Schema is exported to consumers via `package.json`'s `"./schemas/*"`, but
**no test or build step validates against it**, and the enforced validator
`validateFlavor` (`src/index.ts`) never checks the `name` field at all — it only
validates `accents`/`surfaces` tokens and the locked-token rule. Because nothing gates
it, the schema can drift from the code (its `name` enum lagged `flavorNames` for a
while after `sliced-bread` landed, until reconciled by hand). Note also that its
`socialCard.composition` enum is the 3-value abstract taxonomy, matching `index.ts`
but not the four rendered card classes — that 3-vs-4 split is intentional, not drift.

Treat `src/flavor.ts` `flavorNames` as the source of truth for the flavor set, not the
schema. If you rely on `schemas/flavor.schema.json`, reconcile it by hand — CI will not
catch a mismatch.

Grounded in: `src/flavor.ts`, `src/index.ts` (`FlavorDefinition`, `validateFlavor`,
`core.lockedTokens`), `src/social-card.ts` (`cardClass`), `src/starlight.ts`,
`preview/scripts/flavor.mjs` (`previewFlavors`), `schemas/flavor.schema.json`,
`styles/social-card.css`, `test/contracts.test.mjs`.
